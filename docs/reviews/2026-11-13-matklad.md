# oers code review, read through matklad's published engineering values

> **Note.** This is Claude reviewing the code. I apply the engineering values Aleksey Kladov
> (matklad) has written about publicly: ARCHITECTURE.md as the codebase's map, "push ifs up
> and fors down", small dependency graphs, testing at boundaries with data-driven tests,
> TigerBeetle's TIGER_STYLE (assertions, static allocation, explicit bounds, deterministic
> simulation), and concrete code over generic code. It is not written by him, it does not
> quote him, and nothing here should be taken as his opinion of this project.
>
> Scope: every tracked `.rs` and `.wgsl` file under `crates/` and `app/` (~12,600 lines; the
> vendored C liboni was skipped) and the `Cargo.toml` files. Read-only: nothing was built,
> run, or changed. Line numbers are for commit `31aa188`.

---

## 1. Summary

The crate split is right, the lossless-recording design is sound, and the tests that exist
are the good kind: oracles, properties, and file-format checks at the boundary. Most of what
follows is one theme. **The invariants the design relies on are written in prose and kept by
convention. They are not asserted, the bounds that keep them true are implicit, and the
simulator doesn't exercise the path where they matter.**

The five points that matter most:

1. **The recorder can die without anyone noticing** (defect D1). If the recorder thread ends,
   `let _ = rec.send(..)` throws every block away, `recording` stays `true`, and the UI keeps
   showing "Recording". Nothing checks whether the recorder thread is alive. This breaks the
   project's priority-1 rule, "lossless or loudly not". It's unlikely to happen, but the
   failure is silent.
2. **The block pool is smaller than the queues it feeds** (D2). There are 256 blocks (273 ms
   of data), but the pyramid, DSP, display and recorder queues hold 2 s, 1 s, 0.5 s and 20 s.
   Whenever a consumer falls behind, the real-time thread allocates on every block. README
   says "no allocation in steady state", and the code doesn't deliver that.
3. **The simulator skips the parser.** `SimBoard::read_block` (`sim_board.rs:251-270`) writes `Block`s directly, so the
   frame parser, gap splitting, the resubmitted `pending` frame, bad-frame counting and the
   recorder's handling of non-contiguous blocks never run together without a board. The
   pieces needed for a deterministic simulation test are already there (`encode_payload`, a
   seeded RNG, `acquisition_loop` taking `&mut dyn Board`). §5 sketches it. It's the biggest
   payoff available for priority 1.
4. **There are almost no runtime assertions.** About 12k lines of production code contain 3
   `assert!` calls, all in `registers.rs`. Where an assertion belongs, the code uses
   *defensive clamps* instead (`.min(len)`, `.max(1)`, padding with zeros, an early `return`)
   that hide broken invariants. The most valuable assertion missing is in the recorder,
   `data.len() == len() * num_channels`. Without it, one bad block would misalign every
   channel of `continuous.dat` from that point on, with no sign of it.
5. **There's no map, and the big GUI files mix model code with drawing.** `CLAUDE.md` is a
   dated session log, not an ARCHITECTURE.md. `views.rs` and `frame.rs` interleave pure
   "row model" functions with 200–240-line egui functions. The CAR window is implemented
   twice, and each copy carries a branch that can never run. Three unbounded growth paths
   (D3–D5) sit in that layer.

## 2. Architecture and shape

### What the shape is

```
oni-sys  (FFI, cc)          → rhythm (driver, pure parser, simulator; 13 crates in its tree)
                            → engine (threads, recorder, DSP, audio, pyramids; 49 crates)
                            → app    (egui/wgpu; 237 crates)
```

The dependency arrows are good. `rhythm` knows nothing about threads or the GUI, `engine`
knows nothing about egui, and the GUI reaches the board only through `Engine`. `Board` is a
trait with exactly two implementations, one for hardware and one for the simulator. That is
justified generality, not speculative.

### Where the shape leaks

- **No ARCHITECTURE.md.** `CLAUDE.md` holds a lot of hard-won knowledge, but it is laid out
  by date ("Status (2026-11-05)", "Added on the rig…"), not by structure. A newcomer, or a
  later session, can't use it to find where things live or which rules must never break.
  matklad's ARCHITECTURE.md idea (bird's-eye view, code map, invariants, boundaries, and
  "what is deliberately *not* here") fits this project well because its invariants are
  unusually crisp. Suggested invariant list, all from the existing code and prose:
  1. The recorder is the only blocking consumer. Every other consumer drops data and
     counts the drops (`lib.rs:509-527`).
  2. A `Block` is contiguous: sample *k* has number `first_sample + k`. A gap always starts
     a new block (`parser.rs:89-91`). The recorder derives `sample_numbers.npy` from this
     (`record.rs:282`).
  3. `Block.data.len() == len() * num_channels`, and `ttl.len() == timestamps.len() == len()`.
  4. Only the recorder thread sets `RecStatus.recording`, and the acquisition thread sends
     `Data` only while it is set (`lib.rs:511`, `record.rs:519,532`).
  5. Display, DSP, audio and review settings never reach a recording. The recorder takes
     the raw `Arc<Block>`.
  6. A trace-window frame reads one snapshot of its settings and queues edits
     (`frame.rs:1-8`).
  7. `continuous.dat` sample index `i` ↔ sample number `first_sample + i`. **This one is
     false after a gap** (see D5), and writing the list down is what exposes it.

  Payoff: a ~1-page file that turns the review-and-change loop from "reread CLAUDE.md" into
  "check the invariant list". Cost: an hour.

- **The "fan-out" is in a 13-argument function.** `acquisition_loop` (`lib.rs:474-487`) has
  `#[allow(clippy::too_many_arguments)]`, four nearly identical `Sender<Arc<Block>>`
  parameters, and an unused `_health: &Health`. A concrete `struct Fanout { rec, lossy:
  [(Sender<Arc<Block>>, &AtomicU64); 4] }` would give the fan-out a name, and that is also
  the seam the simulation test needs (§5).

- **`engine` couples the recording core to the audio device.** `engine/Cargo.toml` pulls in
  `cpal` (with PipeWire) alongside the recorder, so any test of acquisition → recorder
  compiles and links the audio stack. Splitting `audio.rs` into its own crate, or behind a
  feature, keeps the priority-1 core at roughly `rhythm + crossbeam + serde_json + chrono`.
  Cost: low (`AudioMonitor` is already only used by the `audio-feed` worker,
  `lib.rs:357-374`). Payoff: faster test builds, plus a structural guarantee that the
  recording path can't depend on audio.

- **`app.rs` (1218 lines) is a bag of subsystems.** `App` has ~30 fields, which group into:
  spike-tile state (`spike_slot`, `spike_new`, `spike_times`, `spike_reset`, `spike_scroll`,
  `spike_colors`), output-sync state (`ttl_out_word`, `dac_sent`, `outputs_sent`,
  `was_acquiring`), config debounce (`dirty_cfg`), and UI toasts. Each group has its own
  methods already (`drain`/`spike_view`, `outputs_section`/`sync_outputs`). Move each into
  its own struct and file (`SpikeGrid`, `Outputs`), each with a bounded `ingest` and a
  `ui`. This is the "shape of data first" refactor: the struct boundary is where the bound
  in D3 would naturally live.

- **The same settings live in two places.** `OutputSettings` (`config.rs:322`) and
  `BoardSettings` (`types.rs:186-190`) both hold `ttl_output_mode`, `dac_hpf_enabled`,
  `dac_hpf_hz` and `noise_slicer`. `sync_outputs` copies one into the other "so they never
  show up as 'changed'" (`app.rs:651-657`), and `Engine::send_live` copies them a third
  time into `Running::settings` (`lib.rs:278-290`). Data with three sources of truth plus
  synchronisation code is a shape problem. Keeping live outputs out of `BoardSettings`, with
  a single owner, deletes both copies.

- **`views.rs` / `frame.rs` mix the model with egui.** `view_rows`, `chan_key`,
  `chan_filters`, `used_filters`, `set_row_filter`, `view_chinfo`, `band_key`,
  `pyramid_columns` and `sweep_hash` (`views.rs:266-475`) are pure functions of
  `(StreamLayout, TraceViewSettings)`. Together they are the trace-window model, and none
  of them has a test. They sit next to `view_controls` (`views.rs:706-947`, 240 lines of
  widgets) and the two CAR windows. Moving them to `views/model.rs` gives the GUI a
  data-driven test boundary: (layout, settings) in, (row table, chinfo, band key) out. This
  is where per-row filter, CAR and 16-channel-mode bugs would show.

- **`frame.rs::review` (`535-774`, 240 lines) is a state machine with drawing mixed in.**
  The decision logic (pyramid, direct read, append, or wait; when to bump `generation`; when
  `Filling` becomes `Shown`) is the delicate part, and it's interleaved with painter calls.
  The `frame` closure takes 8 positional arguments (`frame.rs:565`). Splitting it as
  "decide, then draw" would let the decision part
  (`fn plan(rv: &ReviewView, key: &Key, pyramid_ok, direct_ok) -> Plan`) be tested from a
  table, the same way `ReviewView::accept` already is (`review.rs:337-351`).

### Accidental generality and dead weight

- **The CAR window is duplicated, and each copy has a branch that can't run.**
  `ViewsShared::car_palette` (`views.rs:1009-1088`) and `App::car_palette`
  (`views.rs:1164-1255`) are ~80 lines each and almost identical. Both `match` on
  `CarTarget`. The view copy is only ever called with `CarTarget::View` (`views.rs:1010`),
  so its `Global` arm (`1025-1028`) is dead. The app copy returns early on `View`
  (`1177`), so its `View` arm (`1189-1191`) is dead. Extract
  `fn car_sets_ui(ui, groups, &mut ViewCar) -> bool` and delete `CarTarget` from both.
- **Leftovers from the removed four-preset filter.** `FilterBank::fsec: [u32; 4]`
  (`traces.rs:92`) and the shader's `& 3u` (`traces.wgsl:74`) still assume four presets,
  but only two exist. `IngestU::nsec` is always written as 0 (`traces.rs:405`) and the
  shader never reads it. The `uv_by_filter` value 0 falls back to `uv_per_row`
  (`config.rs:139-141`, `229-232`), a second fallback level kept only for old configs,
  which `migrate_view_presets` already rewrites.
- **Unused code.** `BandSpec::LFP` (`dsp.rs:105`), `Biquad::notch` (`dsp.rs:72`), and the
  Zcheck/impedance setters, `set_dig_out_high` and `set_amp_powered`
  (`registers.rs:164-207`, `465-489`) have no callers except `regdump`. The literal port
  is a fair reason to keep `registers.rs` whole, but then the golden test (§5.3) should
  cover them. Otherwise, delete until impedance is ported.
- **The same constants appear several times.** The headstage slot names are in
  `oni_board.rs:67`, `sim_board.rs:212` and `headless.rs:33`. The ADC volts-per-bit is in
  `parser.rs:14` and as a literal in `sim_board.rs:190,225`. The µV-per-bit `0.195` is a
  literal in `oni_board.rs:882` while `ELECTRODE_UV_PER_BIT` exists. Chip IDs are split
  between `parser.rs:13` and `oni_board.rs:57-60`, and each module imports from the other.

### Push ifs up, fors down

The CPU per-sample paths put the loop above and the branch below:

- `dsp_thread` (`lib.rs:551-560`): for every sample it re-matches `(&cur.car, &car_mask)`
  and then, per channel, evaluates `mask.get(ch).copied().unwrap_or(false)` before calling
  `bank.tick(ch, x)`, which slices `state[ch*ns..]` again (`dsp.rs:133-140`).
- `band_filter` (`pyramid.rs:402-416`) checks `!bl.car_ref.is_empty()` on every sample.
- `Car::mean` (`dsp.rs:16-25`) calls `row.get(ch)` per reference channel per sample.

A block API, `FilterBank::process(&mut self, data: &[i16], nch, car: Option<&CarPlan>, out:
&mut [f32])`, resolves the CAR choice once per block and runs a tight loop per channel. The
GPU `filt` pass already works this way. Payoff: simpler call sites, and one shared
implementation for the four CPU consumers (DSP, audio, pyramid, slope). Today each
re-implements "CAR then filter" or "filter then CAR" (see §3, oracle test).

### Dependencies

These are modest and justified: `rhythm` has 13 crates, `engine` 49, `app` 237 (wgpu/eframe
account for most of them). Small points:
- `thread-priority` wraps two `libc` calls, and the code is Linux-only by decision.
- `bytemuck` is already a dependency of `engine`, but `record.rs` still uses hand-written
  `unsafe` slice casts (D10).
- No `[workspace.lints]` section. Clippy lint drift between toolchains is mentioned in
  CLAUDE.md, and a pinned `rust-toolchain.toml` plus `[workspace.lints]` would stop it.

## 3. Invariants and assertions

TIGER_STYLE says to assert preconditions, postconditions and invariants densely, to crash
on a broken invariant, and to treat assertions as executable documentation. Today:

- **Runtime assertions in production code: 3**, all in `registers.rs:65-73`, plus two
  `const` asserts (`dsp.rs:353`, `pyramid.rs:54`). There is no `debug_assert!` anywhere.
- **Defensive clamps where an assertion belongs.** Each of these hides a broken invariant:

| Site | What it silently tolerates | Should be |
|---|---|---|
| `views.rs:119-123` `ViewState::push`: if `b.ttl.len() != n`, pads with zeros | a block whose TTL and sample counts differ; the code makes up TTL words | `assert_eq!(b.ttl.len(), n)` |
| `views.rs:129`, `frame.rs:324` `.min(vs.pending_ttl.len())` | `pending` and `pending_ttl` drifting out of lockstep | `debug_assert_eq!(pending.len(), pending_ttl.len()*nch)` |
| `pyramid.rs:203-205` `ingest` returns if `start` isn't bucket-aligned | a caller bug becomes a permanent coverage hole the backfill can't explain | `assert!(start % BUCKET == 0)` (the test at `799-801` pins the silent behaviour) |
| `pyramid.rs:222` `ttl[o..(o+B).min(ttl.len())]` | short TTL slices | `assert!(ttl.is_empty() \|\| ttl.len()*nch == data.len())` |
| `traces.rs:361`, `387`, `spikes.rs:114,117` `.min(nch)` / skip mismatched spikes | wrong table sizes reaching the GPU | asserts at the `TraceFrame` constructor |
| `nch.max(1)` in `pyramid.rs:149,639`, `review.rs:75,80`, `frame.rs:652-653`, `views.rs:118,628` | an `nch == 0` layout reaching code that can't mean anything with it | one `assert!(nch > 0)` where the layout is accepted |
| `sim_board.rs:255`, `lib.rs:316` `block_samples.max(1)` | a 0 in config | validate `BoardSettings` once (`fn validate(&self) -> Result`) |

- **The missing assertion that matters most** is in `Recording::write_block`
  (`record.rs:261-284`). It checks `num_channels`, which is good, then writes `b.data` raw.
  If `data.len() != len() * num_channels`, every later sample in `continuous.dat` is shifted
  by the difference: channels rotate, and nothing reports it. The same goes for
  `ttl.len()`/`timestamps.len()`, where a mismatch would index `b.timestamps[i]` out of
  bounds (`record.rs:304`) and panic, which is then D1. Add, at the top of `write_block`:
  ```rust
  assert_eq!(b.data.len(), b.len() * b.num_channels);
  assert_eq!(b.ttl.len(), b.len());
  assert!(self.next.is_none_or(|n| b.first_sample >= n)); // monotonic; gaps allowed
  ```
  and the matching postcondition at the end of `RhythmParser::parse` (`parser.rs:145-148`)
  and `SimBoard::generate_sample`.
- **Sentinels instead of types.** `SpikeDetector::pending: Vec<(i64, usize, f32)>`
  (`dsp.rs:277`) uses `peak_v != 0.0` as "nothing pending" (`dsp.rs:338`). A spike whose
  filtered trough is exactly 0.0 can't happen with `thr < 0`, but `Option<Pending>` would
  say so through the type. There is also an empty `if pend.1 == 0 { }` with only a comment
  inside (`dsp.rs:327-329`).
- **Crash on bugs, report on environment.** The code handles environment errors well:
  `anyhow` errors from disk and USB surface in the UI. But a *bug* (a panic) in a worker
  thread only kills that thread, and nobody hears about it (D1). With npy headers rewritten
  every second, the recording format is already crash-consistent. That makes
  `panic = "abort"` in `[profile.release]` cheap and safe: any invariant violation ends the
  process, and the files on disk stay readable up to the last second. This is the
  TigerBeetle position, and here the file format already pays for it.

## 4. Bounds

TIGER_STYLE wants every queue, loop and buffer to have an explicit upper bound you can see
at its definition. Inventory:

| Queue / buffer | Bound | Visible? |
|---|---|---|
| display / dsp / audio / pyramid channels | `bounded(blocks_per_s/2+4)` etc. (`lib.rs:328-332`) | ✅ named, commented |
| spike channel | `bounded(20_000)` (`lib.rs:333`) | ✅, but drops aren't counted (`lib.rs:567`) |
| **recorder channel** | `unbounded()` (`lib.rs:119`), held to `rec_limit` by polling `rec.len()` with a 200 µs sleep loop (`lib.rs:513-515`) | ⚠️ the bound is in the producer, not in the channel |
| live-command channel | `unbounded()` (`lib.rs:326`) | ⚠️ bounded only because a human clicks |
| review request/response | `unbounded()` (`review.rs:46-47`) | ⚠️ bounded only by "one `Filling` per view" in `frame.rs:599,624` |
| review reader's open files | `HashMap<PathBuf, File>`, never evicted (`review.rs:51`) | ⚠️ one fd per recording ever reviewed |
| **block pool** | `POOL = 256` (`lib.rs:489`) | ❌ smaller than the queues it feeds (D2) |
| per-view `pending` | one window (`views.rs:124-134`) | ✅ commented |
| **`App::spike_new`** | none (`app.rs:227`) | ❌ D3 |
| pyramid RAM | `Store::budget` (`pyramid.rs:350-373`) | ✅ but see D4 |
| `Sweeps::pending` | none stated (`sweep.rs:42,60`), drained each frame | ⚠️ |
| `Notes::notes` | per acquisition (`notes.rs:46`) | ⚠️ fine in practice |
| `SimBoard::active` | units × 5 × template, implicit | ⚠️ |
| scan loop | `while t < n` that skips non-Rhythm frames with no limit, blocking reads (`oni_board.rs:532-550`) | ❌ D6 |
| `stop_acquisition` join | waits for a thread that may be blocked in `oni_read_frame` (`lib.rs:416`, `oni_board.rs:1062`) | ❌ D6 |
| PLL / calibration / BNO polls | 2 s / 2 s / 1 s timeouts (`oni_board.rs:398-403, 464-470, 652-660`) | ✅, and they are marked `DIFF:` where upstream polls forever. Exactly right. |

The fix for the recorder queue costs one line. `bounded(rec_limit)` with a blocking `send`
*is* the back-pressure the comment describes. It also measures the wait directly instead of
polling `len()`, and it removes the separate `rec_limit` arithmetic. The protocol messages
(`Start`, `Stop`, `Message`) would then share that bound, which is fine: they're tiny and
rare. If they must never wait behind data, give them their own small channel.

## 5. Testing

### 5.1 What is already good (and matches these values)

- **Oracle tests.** `every_level_matches_brute_force` (`pyramid.rs:685-729`) checks the
  incremental pyramid against brute-force min/max over pieces ingested out of order.
- **Property tests that encode the user's requirements**, not the implementation:
  `held_gain_does_not_track_firing_rate`, `hash_remains_audible_at_default_depth` and
  `expander_preserves_relative_unit_amplitudes` (`audio.rs:675-715`). They survive any
  refactor of `MonitorDsp`, which was deliberately separated from the device to make it
  testable (`audio.rs:184`).
- **Boundary tests.** `writes_valid_open_ephys_binary` (`record.rs:586-662`) goes from
  messages in to files out and re-parses the npy headers. `Notes::handle` is tested from
  egui events to finished notes (`notes.rs:219-272`). The config migration is tested
  against real old JSON (`config.rs:460+`).
- `encode_payload` (`parser.rs:152-174`) is the parser's inverse. That's the right tool,
  and it's half of a simulation test already.

### 5.2 What is missing

- `crates/engine/src/lib.rs` (acquisition loop, fan-out, lifecycle), `oni_board.rs`,
  `sim_board.rs`, `views.rs` and `frame.rs` have **0 tests**.
- No end-to-end test covers gap → split block → non-contiguous `sample_numbers.npy` → TTL
  edges across the gap → `health.dropped == gap`.
- The recorder's message protocol (Data after Stop, Start without acquisition, I/O error
  mid-block, Message before the first block, AcquisitionStopped while recording) is
  covered only on the happy path.
- README says the register lists are "verified byte-identical to Intan's C++". `regdump`
  produces the comparison output, but the expected output isn't checked in, so the claim
  can't be reproduced in CI (§5.3).
- **No oracle ties the four CAR+filter implementations together**: `dsp_thread` does CAR
  then filter in µV (`lib.rs:558-559`), `band_filter` filters in LSB then applies CAR
  (`pyramid.rs:405-415`), the shader filters in physical units then applies CAR
  (`traces.wgsl:77-128`), and the slope trigger does CAR then filter (`frame.rs:360-361`).
  `dsp.rs:5-7` argues these are equivalent, which is true while every channel uses the same
  linear filter. One test feeding the same synthetic block through the three CPU paths
  would pin that down. The comment `pyramid.rs:9` ("exactly as the shader applies it") is
  currently backed by nothing.

### 5.3 Cheap wins

1. **Golden register test.** Check in the C++ harness output (or its sha256) under
   `crates/rhythm/testdata/` and compare it with `regdump` in a `#[test]`. That's 20 lines,
   and it locks in the most safety-relevant port in the tree.
2. **Recorder table test.** Extract the loop body of `run_recorder` (`record.rs:454-552`)
   into `Recorder::on(&mut self, msg) -> ()` with the state in a struct. Then write a
   table of message sequences and the expected files, `RecStatus` and error.
3. **Model tests for the trace windows** (after the `views/model.rs` move): a table of
   (layout with RHD2132 16-ch + RHD2216 + AUX/ADC, settings) → `view_rows`, `view_chinfo`
   flags, `band_key`.

### 5.4 Proposal: deterministic simulation of acquisition → recorder

This is the TigerBeetle "VOPR" idea scaled to this project. One seed determines everything:
the board's frame stream including faults, the disk's behaviour, and the timing of user
actions. The run is single-threaded with virtual time, and at the end a checker proves the
recording is exactly what the board sent, minus the drops that were counted.

**Seams needed** (each one also makes the production code better):

1. **A `FrameSource` under `OniBoard::read_block`.** `read_block` (`oni_board.rs:1054-1095`)
   is board-independent logic: take the pending frame or read one, route by `dev_idx`,
   parse, split on discontinuity, count. Pull it out to work over
   ```rust
   trait FrameSource { fn next(&mut self) -> Result<RawFrame<'_>>; }   // dev_idx, time, bytes
   ```
   with `liboni::Context` as one implementation and `SimFrames` as the other. `SimFrames`
   is `SimBoard`'s signal model (unchanged, already seeded: `sim_board.rs:81, 110`) emitting
   `encode_payload` bytes, plus a seeded fault plan: drop *k* frames, corrupt the magic,
   truncate a frame, jump the counter, wrap it at `u32::MAX`, interleave memory-monitor
   frames. Then **`SimBoard` runs the same parser as the hardware**, which today it doesn't
   (`sim_board.rs:251-270` builds `Block`s directly).
2. **Time as a parameter.** `SimBoard` sleeps to pace itself (`sim_board.rs:260-264`), the
   acquisition loop calls `Instant::now()` (`lib.rs:504, 512`), and the recorder
   checkpoints on `Instant` (`record.rs:322`). Pass `now` in. `SimFrames` gets a `paced:
   bool`, so the GUI still runs in real time and the test runs as fast as it can.
3. **`acquisition_loop` as a step function.** `fn step(board, &mut Fanout, rec_sink) ->
   Result<()>` does one block. The thread wrapper becomes a `while !stop { step() }`.
4. **A recorder state machine** (from §5.3 item 2) and a fault-injecting writer. Either a
   root on a tmpfs with a `FailAfter { bytes }` hook in `NpyFile`/`StreamFiles`, or the
   recorder made generic over `W: Write + Seek` in tests only. A seeded "disk stall" means
   the step loop withholds `Recorder::on(Data)` for *n* virtual ms, which exercises
   back-pressure and the `rec_limit` path.

**Driver (sketch):**

```rust
#[test]
fn simulated_acquisition_records_exactly_what_was_accepted() {
    for seed in 0..500 {
        let mut rng = Rng(seed);
        let plan = FaultPlan::random(&mut rng);           // drops, corruption, wraps, stalls
        let mut src = SimFrames::new(layout_rhd2132_16ch_plus_2216(), plan.clone(), seed);
        let mut board = FrameBoard::new(&mut src);         // the extracted read_block
        let mut rec = Recorder::new(tmpdir(seed));
        let mut oracle = Oracle::default();                // what the parser accepted
        for tick in 0..30_000 {
            if plan.user_starts_recording_at(tick) { rec.on(RecMsg::Start) }
            if plan.user_stops_at(tick)            { rec.on(RecMsg::Stop) }
            let blk = board.read_block()?;                 // same code as hardware
            oracle.observe(&blk, rec.is_recording());
            if rec.is_recording() && !plan.disk_stalled(tick) { rec.on(RecMsg::Data(blk)) }
            if plan.crash_at(tick) { truncate_files_randomly(&mut rng); break }
        }
        check(&tmpdir(seed), &oracle, &board.health());     // the invariants below
    }
}
```

**Checker invariants** (each is one of the design's promises):
- `continuous.dat` is exactly the accepted samples of each recording, in order, with no
  duplicates.
- `sample_numbers.npy` is strictly increasing, and the sum of its jumps equals
  `health.dropped_samples` within the recording.
- `health.discontinuities` equals the number of injected gaps. `bad_frames` equals the
  injected corruptions.
- TTL `states`/`full_words` replayed from `initial_state` reproduce every per-sample word.
- After a simulated crash (files truncated at a random byte), every `.npy` header still
  parses and `shape ≤ records present`. This is the "a crash leaves readable files" claim
  from README.
- The review reader and pyramid backfill map samples correctly across gaps. This would
  have caught D5.

**Cost:** about 400–600 lines including the extractions. None of it touches hardware code
paths, except that `OniBoard::read_block` becomes a thin call into the shared function.
**Payoff:** the project's priority-1 property is checked on the dev box (no board) over
thousands of fault schedules per minute, and every future parser or recorder change is
checked against it. The existing `headless --sim` soak becomes a `--check` mode of the same
oracle.

What stays out of scope: liboni/D3XX behaviour (the hang in D3XX 1.1.x isn't
simulable) and the GUI. `OERS_UI_SCRIPT` is a useful harness, but it's wall-clock driven,
so it can't be made deterministic without virtualising egui's time.

## 6. Concrete defects, ranked

Severity is the consequence for the user if the defect fires. Confidence is mine that the
code behaves as described.

### D1. Recorder thread death is silent; data discarded while the UI says "Recording"
**Severity: high (violates priority 1). Likelihood: low. Confidence: high.**

- `lib.rs:520`: `let _ = rec.send(RecMsg::Data(blk.clone()));` ignores the `SendError`
  you get when the receiver is gone.
- `lib.rs:108,123,454`: `rec_thread` is joined only in `Drop`. `Engine::poll`
  (`lib.rs:198-226`) checks `acq.is_finished()` but not the recorder.
- `RecStatus.recording` is cleared only by the recorder itself (`record.rs:452, 485, 532,
  548`). If that thread panics, the flag stays `true`, `App::top_bar` keeps the red
  "Recording" button (`app.rs:284`), and the byte counter just stops rising.
- Lossy consumers have the same blindness: `lib.rs:524` counts only
  `TrySendError::Full`. A dead `dsp`/`pyramid`/`audio` worker returns `Disconnected`,
  which isn't counted or shown. The review then sits at "building the overview" forever.

*Scenario:* any panic in the recorder (an index out of bounds from a malformed block at
`record.rs:304`, an OOM in `serde_json::to_string_pretty`, a future bug). Every block after
that is lost and the UI looks normal.
*Fix:* treat `rec.send` failure as a fatal acquisition error (return `Err` from the loop),
check `rec_thread.is_finished()` and every `workers[i].is_finished()` in `poll`, count
`Disconnected` separately, and consider `panic = "abort"` (§3).

### D2. The block pool is smaller than the queues, so the RT thread allocates whenever a consumer lags
**Severity: medium (latency risk in the SCHED_FIFO thread, and it breaks a stated
guarantee). Confidence: high.**

- `lib.rs:489`: `const POOL: usize = 256;` with 32-sample blocks (`types.rs:227`) at
  30 kHz is 273 ms of blocks.
- Queues: display `938/2+4 = 473`, DSP `942`, pyramid `1880` (`lib.rs:328-332`), recorder
  `rec_limit = 18750` (`lib.rs:338`).
- `lib.rs:499-503`: if a slot is still referenced, a fresh `Block::default()` is
  allocated, and its three `Vec`s then grow by repeated reallocation in `read_block`.

The pyramid builder is *designed* to lag (it runs at `SCHED_IDLE` with a 2 s queue,
`pyramid.rs:433`), and the recorder lags under disk stalls, which is exactly when the RT
thread matters most. During those stretches the acquisition thread does 3+ allocations per
block (~3000/s). README "Reliability design" says "no allocation in steady state".
*Fix:* size `POOL` from the queue capacities (sum of bounds + in-flight + 2), or have the
consumers return blocks through a free list (a bounded `Sender<Arc<Block>>` back to the
acquisition thread). Then assert in debug builds that the fallback allocation never runs.

### D3. `App::spike_new` grows without bound while the main window is hidden
**Severity: medium (memory growth in long sessions; a burst of GPU writes when the window
reappears). Confidence: medium-high.**

- `app.rs:227` pushes every detected spike into `spike_new` inside `drain()`, which
  `logic()` calls on every pass (`app.rs:970`), including while the root window is hidden.
  CLAUDE.md: "Board polling, outputs and spike intake run in `App::logic`, which eframe
  keeps running while the root is hidden."
- It is drained only by `spike_view` (`app.rs:860`), which runs from `ui()` and so only
  while the main window is drawn, or by `reset_views` (`app.rs:371`).

*Scenario:* the user parks the main window on another workspace and works in the Port A/B
trace windows for hours, which is the layout CLAUDE.md describes. At ~60 channels × ~10–20
Hz, that's ~1000 `Arc<Spike>`/s (each a 40×f32 waveform plus header), so ~0.5–1 GB/h. When
the window is shown again, `SpikeCallback::prepare` issues one `write_buffer` per stored
spike (`spikes.rs:116-123`).
*Fix:* only the newest `SLOTS` per channel can ever be shown. Keep `spike_new` as a
per-channel ring of at most `SLOTS` entries (`nel × 48` total), which is also a visible
bound.

### D4. The pyramid keeps ingesting live data after the recording stops
**Severity: low-medium (RAM, and a recording's review detail released for data that was
never recorded). Confidence: medium-high.**

- `RecStatus.source` is set when a recording starts (`record.rs:467-468`) and never
  cleared. The doc comment says "(or the last one)" (`record.rs:417-419`).
- `pyramid_thread` keeps folding live blocks for as long as
  `b.first_sample >= src.first_sample` (`pyramid.rs:488-491`), so it continues after Stop
  until acquisition restarts.

*Scenario:* the user records 10 minutes, stops, and keeps acquiring for 3 hours (a common
pattern: record trials, watch in between). The pyramid grows by ~0.7 GB/h of data that
isn't in any file, and when it reaches `review_ram_gb` (1.5 GB) `enforce_budget` releases
level-0 chunks starting with *the real recording's*. Review still clamps to the file length
(`frame.rs:233,545`), so the user sees nothing wrong, only more file reads later and an
idle-priority thread using CPU for nothing.
*Fix:* stop ingesting at the recording's end. Either clear or mark `source` on `Stop`
(the review reader still needs the path, so add `ended_at: Option<i64>`), or gate the
pyramid on `status.recording`.

### D5. Review and pyramid backfill treat file offset as sample number, which breaks after a gap
**Severity: low-medium (display only, after an event that is already reported loudly).
Confidence: high on the code; I didn't measure the visual effect.**

- `review.rs:91`: `let start = (r.from - r.src.first_sample).clamp(0, avail);` turns a
  sample number into a file offset.
- `pyramid.rs:602`: the backfill reads at `(c0 - lead) * nch * 2`, a file offset, while
  live ingestion indexes by `b.first_sample - src.first_sample` (`pyramid.rs:493`), a
  sample number.
- `continuous.dat` has no holes. After a hardware gap of *g* samples, file index *i* holds
  sample `first_sample + i + g`.

*Effect after a gap:* review traces shift *g* samples relative to the review time axis, to
TTL lanes (`TtlEdges` uses true sample numbers from `sample_numbers.npy`,
`review.rs:128-133`) and to note markers. In the pyramid, live-ingested and backfilled
stretches use different coordinates, so the raw pyramid ends up spliced inconsistently.
*Fix:* `RecSource` carries a gap list (the recorder knows each discontinuity because it
writes `sample_numbers.npy`), and one `fn sample_to_offset(&self, s) -> Option<u64>` is
used by both readers. This is exactly what the simulation test's gap invariant (§5.4)
checks.

### D6. Unbounded waits: Stop and port scan can hang on a silent board
**Severity: low-medium (GUI freeze; recording data already written is safe). Confidence:
low-medium (depends on how liboni/D3XX behave when the board stops streaming without an
error).**

- `lib.rs:416`: `stop_acquisition` joins the acquisition thread on the GUI thread. That
  thread checks `stop` only between blocks (`lib.rs:492`), and inside `read_block` it
  blocks in `oni_read_frame` (`oni_board.rs:1062`).
- `oni_board.rs:532-550` `read_scan_block`: `while t < n` with blocking reads, where
  non-Rhythm frames `continue` without advancing `t`. A board that never sends Rhythm
  frames leaves the "scan ports" job busy forever (`Engine::is_busy`), and the board can't
  be reopened. The same function slices `&f.data()[8..]` and `d[0..8]` (`537-538`) without
  a length check, so a short frame panics. That panic is caught as "thread panicked (board
  lost)".

*Fix:* a deadline on both loops (as the PLL wait already does, `oni_board.rs:397-403`),
and in `stop_acquisition` a bounded wait with a clear error ("acquisition thread did not
stop; board may be wedged") instead of an indefinite `join`.

### D7. A config that fails to parse is replaced by defaults, which then overwrite it
**Severity: low (lost settings; recordings may go to the default root). Confidence: high.**

`config.rs:388-395` logs a warning and uses `Config::default()`. The next debounced
`save_cfg` (`app.rs:1011-1014`) writes the defaults over the user's file. That includes
`record_root`, which reverts to `~/oe-recordings` (`config.rs:374`) with only a log line.
*Fix:* on a parse error, rename the file to `config.json.bad-<time>` first and show it in
the error bar.

### D8. `OniBoard::apply_settings` commits the new settings before the hardware accepts them
**Severity: low. Confidence: high.**

`oni_board.rs:1001-1002` sets `self.settings = new.clone()` and then performs register
writes with `?`. If one fails partway (USB error, PLL timeout at `:401`), `settings()`
reports values the board doesn't have. The GUI then shows the change as applied
(`app.rs:527`) and records with a layout derived from it. *Fix:* apply to a local copy and
assign `self.settings` only on success. Or, on error, mark the board as needing a reopen.

### D9. `Recording::finish` writes metadata before syncing data, and stops at the first error
**Severity: low. Confidence: high.**

`record.rs:370-379` writes `structure.oebin` first, and if that fails, the `?` skips the
flushes and `sync_all` of every data file. They are only flushed by `BufWriter`'s drop,
which ignores errors, with headers up to 1 s stale. *Fix:* sync the data first, then
write the metadata, and collect errors instead of returning early.

### D10. `NpyFile::write<T: Copy>` is an unsound-by-signature transmute
**Severity: low (no current misuse). Confidence: high.**

`record.rs:75-76` reinterprets any `T: Copy` as bytes. A `Copy` type with padding would
write uninitialised bytes. `record.rs:278` and `317` do the same by hand. `bytemuck` is
already an `engine` dependency: use `T: bytemuck::Pod` and `bytemuck::cast_slice`.

### Smaller defects
- **Spike drops aren't counted.** `lib.rs:567`: `let _ = spikes.try_send(sp);`. Every
  other lossy path has a counter.
- **Allocation per block in the `audio-feed` and `dsp` threads.**
  `self.settings.lock().clone()` (`audio.rs:401`, `lib.rs:542`) clones `Vec`s ~940×/s, and
  `MonitorDsp::process` builds a key with `s.channels.clone()` per block
  (`audio.rs:213`). A generation counter (`AtomicU64`, bumped on edit) clones only on
  change.
- **The audio callback takes a lock it doesn't need.** `audio.rs:330-343` wraps the
  `rtrb::Consumer` in `Arc<Mutex<…>>` and `try_lock`s it in the audio callback, only
  because `build` may be called twice. Pass the consumer through an
  `Option<Consumer>`/`take()`, and the real-time callback owns it outright.
- **A sleep used as synchronisation.** `app.rs:1081-1083` stops the recording, sleeps
  50 ms on the GUI thread, then stops acquisition. The recorder channel is FIFO, so `Stop`
  is processed before `AcquisitionStopped` anyway. The sleep adds nothing and suggests an
  ordering dependency that doesn't exist.
- **Doc drift.** `record.rs:16`: "The recorder thread receives every block while acquiring
  (recording or not)". In fact the acquisition thread sends only while recording
  (`lib.rs:511`).
- **Data that arrives after `Stop` is dropped silently** (`record.rs:462`). That is correct
  per the protocol, but counting it (`data_after_stop`) would make a protocol bug visible.

## 7. Smaller notes

- **Rust/WGSL struct layouts aren't checked against each other.** `IngestU`, `CutU` and
  `RenderU` (`traces.rs:19-72`) and the spike shader's `U` (`spikes.rs:12-23`) are
  maintained by hand next to their WGSL twins. `const _: () =
  assert!(size_of::<RenderU>() == 80);` and friends cost nothing.
- **The "4 sections" limit appears in three places**: `FilterBank::new`'s `take(4.min(..))`
  (`traces.rs:105`), the shader's `min(fs >> 8u, 4u)` and `array<f32, 8>`
  (`traces.wgsl:69,76`), and the test (`traces.rs:501`). Make it one `const` mirrored in
  WGSL with a comment, and have `FilterBank::new` assert instead of truncating.
- **Flags travel as a float.** `chinfo.y` is a `f32` decoded with `u32(x + 0.5)`
  (`traces.wgsl:50-52`). It works, but a separate `array<u32>` (or packing into `vec4<u32>`)
  says what it is.
- **The per-frame model is recomputed from scratch.** `chan_key` is O(channel index), and
  `chan_filters`, `band_key` and `view_rows` run on every frame and for every window
  (`views.rs:266-283, 565-575`). That's harmless at 64 channels. Once these functions move
  into a model struct, it can cache on a `(layout_key, settings)` change, which also
  removes the `last_cfg`/`tables_key`/`last_chinfo` change-detection fields in `ViewState`
  (`views.rs:47-50`).
- **`Engine.last_error` is a `pub` field** written by `App` in five places (`app.rs:274,
  949, 1043`, `lib.rs:208-218, 419-423`). A `fn report(&mut self, e)` keeps one writer.
- **The slope trigger and the spike detector implement "crossing" differently.** The
  detector fires on `v < thr` when not dead (`dsp.rs:330`). The slope trigger needs
  `prev >= level && x < level` (`slope.rs:96`). The module doc says the sweeps "match the
  spike tiles". Share one `Crossing` core, or document the difference.
- **Hidden configuration.** `SimBoard::new` reads `OERS_SIM_ARTEFACT` from the environment
  (`sim_board.rs:85`). Passing it in from the caller keeps the simulator's behaviour a
  function of its arguments, which the simulation test (§5.4) needs.
- `apply_dac` threshold: `((thr / 0.195) + 32768.0).abs() as i32` (`oni_board.rs:882`).
  The `.abs()` only matters below −6.4 mV, where the `clamp(0, 65535)` would handle it
  anyway, so the intent is unclear.

## 8. What is already good

- **The priority-1 design is right and simple.** One blocking consumer, every other
  consumer lossy with a counter, back-pressure into the board's DRAM, every sample's
  hardware counter checked, and gaps split into blocks rather than papered over
  (`parser.rs:84-99`). There is a test for "gaps without double counting"
  (`parser.rs:241-263`).
- **The parser is a pure function** over `&[u8]` with an explicit inverse
  (`encode_payload`). That is the most testable shape a driver can have.
- **The port is disciplined.** `DIFF:` markers wherever behaviour differs from upstream,
  and only to make failures visible (`oni_board.rs:4-5, 397`). The register module is a
  literal port with the upstream quirk reproduced and commented (`registers.rs:258-260`).
  The hardware-safety audit is in CLAUDE.md.
- **The file format is crash-consistent by construction.** Npy headers are padded to a
  fixed length and rewritten every second (`record.rs:59-93`). The config uses
  write-then-rename (`config.rs:425-431`).
- **Bounds were thought about where they caused trouble.** The per-view `VecDeque` window
  with a comment explaining the earlier freeze (`views.rs:35-38`), chunked GPU uploads
  under the 128 MB binding limit (`frame.rs:305-308`), and the pyramid RAM budget with an
  explicit release policy and a test (`pyramid.rs:731-781`).
- **`ViewFrame` + `Edit`** (`frame.rs:1-8, 36-48`) is a clean answer to "one frame, one
  snapshot of settings". It's essentially a command queue, and the right shape for
  immediate-mode UI.
- **The audio chain encodes the user's domain requirements as tests.** Texture is
  preserved, the gain is held, the limiter is linear below the knee. These tests describe
  *what must stay true*, so they will survive refactors.
- **Comments explain *why***, not what: the servo's "after this callback" reasoning
  (`audio.rs:348-351`), the D3XX version trap, the VecDeque history.
- **The code is concrete.** Linux-only, two `Board` implementations, no plugin system
  built before it's needed (CLAUDE.md "Not yet ported": processor graph deferred).
  Dependencies are small for the non-GUI crates.
