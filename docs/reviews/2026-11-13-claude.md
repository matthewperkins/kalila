# oers code review (Claude)

Scope: every tracked `.rs` and `.wgsl` under `crates/` and `app/`, read in full (vendored liboni read only where needed to check FFI lifetimes). Read-only; nothing was built or run.

## Summary

The acquisition → recorder path is sound, and no finding puts recorded samples at risk in normal operation. The parser detects gaps without double counting. The recorder is FIFO-ordered against Start/Stop and back-pressured into board DRAM. The lossy consumers can't stall it. The FFI wrapper is correct w.r.t. liboni's refcounted frame buffers.

The most valuable findings are in the newer review/pyramid layer and in settings identity:

1. The pyramid backfill band-filters **while holding the store mutex** that every GUI frame takes. During a backfill the windows stall for tens to hundreds of ms per chunk, for minutes, and the holder runs at `SCHED_IDLE`.
2. The raw pyramid is **not reset when acquisition restarts**. A later acquisition's samples get folded into the previous recording's overview, so review shows wrong data.
3. Review and backfill map sample numbers to file offsets **assuming no gaps**. After any dropped samples, traces, TTL lanes and notes misalign.
4. DAC routes (including threshold→TTL-out), CAR sets and audio channels are stored as **global electrode indices**. They silently point at different electrodes after a layout change such as the 16-ch toggle.
5. Changing the recording root mid-session has **no effect** until a new session starts.

The rest are lower-severity robustness issues: panic containment, a parser edge case, finalisation on I/O error, and config overwrite on a parse error.

---

## Findings (most severe first)

### 1. Backfill filters inside the pyramid lock; every GUI frame waits on it (priority inversion with a SCHED_IDLE holder)
- **Where:** `crates/engine/src/pyramid.rs:607-626`. GUI side: `app/src/app/views.rs:567` (`ViewsShared::drain`, called by the main window and by every trace window each frame), `app/src/app.rs:351` (`health_chips`), `app/src/app/views/frame.rs:603`.
- **What:**
  ```rust
  let mut st = store.lock();                 // pyramid.rs:607
  st.backfilling = true;
  ...
  Some(v) => { ...
      let mut tmp = band_live(&bl.key, fs);
      band_filter(&mut tmp, &data, nch, &mut fb);   // IIR over CHUNK + lead samples × chans, under the lock
  ```
  The live path deliberately filters outside the lock (`// Filter outside the lock`, line 516). The backfill path doesn't. The chunk is `CHUNK = 61 440` samples plus `lead = 3/f_low` s (`BandKey::lead`, line 79). The GUI allows `band_low_hz` down to 0.1 Hz (`config.rs:247` clamps to ≥ 0.1).
- **Why it matters:** priorities 2–3 (display latency). Every window's frame does `self.pyramids.lock()` in `drain()`, so all oers windows block while the builder filters. The holder runs at `SCHED_IDLE` (`pyramid.rs:433`), so under CPU load it can be descheduled while holding the lock. That is classic priority inversion.
- **Failure scenario:** a Port B window with Band 10 Hz– (Myomatrix) and 32 electrodes. Change the corner during a 1 h recording. The backfill then runs about 1800 chunks of 61 440 + 9 000 samples × 32 channels × 4 biquads, about 2.3 M channel-samples per chunk, roughly 20–40 ms under the lock. There is only a 10 ms pause between chunks (`CHUNK_PAUSE`). For the few minutes the rebuild takes, every GUI frame can wait up to ~40 ms, so the display drops to ~20 fps with tens of ms added latency. With a 0.1 Hz corner the lead is 900 000 samples (30 s), so a single hold is ~0.3–0.5 s and the windows visibly freeze repeatedly. With a 1 Hz corner the lead is 90 000 samples. The raw-pyramid backfill (`raw.ingest` of 61 440 × 62 under the lock) is cheaper but has the same shape.
- **Suggested fix:**
  - Run `band_filter` (and the raw min/max reduction, if you like) before `store.lock()`, exactly like the live path. Take the lock only for `p.ingest`. Better: compute the bucket min/max outside too and pass finished buckets in.
  - Consider capping `lead` relative to `CHUNK`, or processing a hole oldest-first so the filter state carries across chunks. With a 0.1 Hz corner each 2 s chunk currently refilters 30 s.
- **Severity:** medium (display only, but against the stated latency goal, and it can freeze the UI during an experiment). **Confidence:** confirmed in code; the timings are estimates from the code's own sizes.

### 2. The previous recording's raw pyramid is overwritten by the next acquisition's samples
- **Where:** `crates/engine/src/pyramid.rs:456-466, 470-479, 488-491`; `crates/engine/src/record.rs:417-419`; `crates/rhythm/src/parser.rs:85-86`; `app/src/app/views/frame.rs:221-243`.
- **What:**
  - The store resets only when `status.source.dat` changes (`pyramid.rs:459`).
  - `RecStatus::source` deliberately keeps "the last one" after a recording stops (`record.rs:417`).
  - Each acquisition restarts sample numbers at 0: the parser's first sample is `0` (`parser.rs:86`), and `SimBoard::start` sets `sample = 0`.
  - The live ingest guard is only `b.first_sample >= src.first_sample` (line 490).
  - A new pyramid thread is spawned per acquisition with empty local `bands`, so `st.add_band` replaces the band pyramids; but `st.raw` is kept.
  - Review is offered whenever `rec_source` exists with the same channel count (`frame.rs:221-233`), not only while recording.
- **Why it matters:** review shows data that is not in the file. That is a correctness problem in a tool used to judge recordings. The recording itself is untouched.
- **Failure scenario:**
  1. Acquire, start recording at t = 60 s (so `src.first_sample` = 1 800 000), record 10 min, stop recording.
  2. Change the analog band and press Apply, which stops and restarts acquisition (`app.rs:531-534`). Or just press Stop then Acquire.
  3. After 60 s of the new run, its blocks satisfy `first_sample >= 1 800 000` and are ingested at `at = first_sample - 1 800 000`, starting at recording position 0.
  4. Level 0 is overwritten (`copy_from_slice`), and coarser levels become the min/max union of both runs.
  5. Reviewing the old recording at spans ≥ 64 samples/column (about ≥ 1.7 s, the pyramid path) now shows the new run's signal, or a mixture. Short direct-read spans still show the file, so the two disagree.

  Also, even without a restart, after a recording stops the builder keeps folding unrecorded live blocks into the store. RAM grows at about 0.7 GB/h until `enforce_budget` starts releasing the **recorded** stretch's fine levels to make room for data that isn't in the file.
- **Suggested fix:** stop live ingest when `!status.recording` or when the acquisition run differs from the one that produced `src`. Give `RecSource` an acquisition-run id (the recorder knows `experiment`), and have the builder ignore blocks from another run. Clamp live ingest to `available(src)` as a backstop.
- **Severity:** medium. **Confidence:** confirmed (code path traced end to end).

### 3. DAC routes, threshold→TTL out, CAR sets and audio channels are global electrode indices: they move to other electrodes when the layout changes
- **Where:**
  - `app/src/config.rs:310-312` (`DacOut::electrode: Option<usize>`, "Global electrode index") and `68-70` (`CarSettings::reference/subtract: Vec<usize>`);
  - `crates/engine/src/audio.rs:58-59` (`AudioSettings::channels`);
  - `app/src/app.rs:631-641` (`sync_outputs` sends `o.dacs[d].electrode` as is);
  - `crates/rhythm/src/oni_board.rs:847-858` (`electrode_to_stream`);
  - by contrast, `views.rs:chan_key` keys per-row filters as `"A1:5"` precisely to survive layout changes.
- **What:** nothing remaps these sets when `layout_key` changes (`app.rs`, `layout_key`, line ~1048). Out-of-range indices are filtered (`e < nel`); in-range indices are reused verbatim.
- **Why it matters:** these settings drive hardware outputs. The DAC comparator with "Threshold → TTL out" can feed closed-loop stimulation (the stimulator plan). They also drive spike detection, audio and the display/pyramid CAR. A silent change of electrode is worse than an error.
- **Failure scenario:**
  1. A1 is a 32-ch RHD2132 and B1 an RHD2216. DAC 3 routes electrode 40 (B1:8) with threshold → TTL out 3.
  2. The user ticks "16-ch RHD2132" for A1 and applies. A1 now has 16 electrodes, so global index 40 is B1:24.
  3. On restart, `sync_outputs(true)` routes B1:24 to DAC 3, and TTL out 3 now fires on a different electrode with no indication.

  The global CAR "reference" set {32..47} (B1) likewise becomes B1:16..31 plus nothing. Spike detection and audio CAR change silently. The same happens after a Rescan that finds headstages in a different order.
- **Suggested fix:**
  - Store these as `chan_key` strings (`"B1:8"`) like `channel_filter`, and resolve them against the current layout.
  - At minimum, detect a `layout_key` change and clear or flag DAC routes and CAR sets with a visible warning.
- **Severity:** medium. **Confidence:** confirmed.

### 4. Review, backfill and the file-length clock assume the file has no gaps
- **Where:** `app/src/review.rs:145-150`; `crates/engine/src/pyramid.rs:493, 600-602, 638-640`; `crates/engine/src/record.rs:278-283`.
- **What:** the recorder appends blocks to `continuous.dat` contiguously and records the true sample numbers in `sample_numbers.npy`, which is correct. Readers turn a sample number into a file position with `from - src.first_sample` (`review.rs:145`). Backfill reads at `(c0 - lead) * nch * 2` (`pyramid.rs:602`). The end of the recording is `first_sample + file_len/(2·nch)`. Live pyramid ingest, TTL edges (`TtlEdges`) and note markers use true sample numbers.
- **Why it matters:** after a gap (DRAM overflow, a USB hiccup: exactly the events `lost N` reports), everything later in review is shifted by the gap length relative to TTL lanes, notes, the "behind live" badge and live-ingested pyramid buckets. Backfilled and live pyramid buckets disagree about where data sits.
- **Failure scenario:** a 3 000-sample (100 ms) gap at 20 min. Reviewing at 30 min, the traces come from file index t − first, i.e. sample t − first + 3000: they are 100 ms *later* than the axis, the laser TTL band and the typed note say. An opto-tagging latency read off review is wrong by 100 ms.
- **Suggested fix:** have the recorder publish the discontinuities in `RecSource`: a small sorted `Vec<(sample_number, file_index)>`, updated as gaps occur. Map through it in `serve`, `available` and backfill. Alternatively, write zero-filled padding and mark it; but the OE format convention is sample_numbers, so mapping is better.
- **Severity:** medium-low (gaps are rare and loudly counted; the recording is correct). **Confidence:** confirmed.

### 5. Changing "Root directory" mid-session is silently ignored
- **Where:** `crates/engine/src/record.rs:496-511`; `app/src/app.rs:289` and `record_section`.
- **What:** `session` (which includes the root) is computed only when `needs_new_session` is true: first recording, forced, or a new day. Afterwards `dir = session.join(experimentN)…` regardless of `status.root`.
- **Failure scenario:** a morning recording goes to `/data/mouseA`. The user changes the root to `/data/mouseB` for the next animal and presses Record. Files go to `/data/mouseA/<morning session>/…/experiment2`, mixing animals. Only the small "Last:" line reveals it.
- **Suggested fix:** remember the root a session was created under, and start a new session when `status.root` differs. Or force `new_session` when the GUI edits the root.
- **Severity:** medium-low (mis-filing, no loss). **Confidence:** confirmed.

### 6. A panic in the acquisition thread leaves the recorder "recording" with no way to stop it from the GUI
- **Where:** `crates/engine/src/lib.rs:385-396, 416-424`; `app/src/app.rs:285` (Record button enabled only `acquiring`), `app.rs` close guard (`close_requested && is_recording → CancelClose`).
- **What:** `RecMsg::AcquisitionStopped` is sent only on the normal return path of the thread closure. On a panic, `stop_acquisition` sees `Err(_)` and reports it, but the recorder still holds `rec` with `recording = true`. Then:
  - `is_recording()` stays true;
  - the Record/Stop button and Ctrl+R are disabled because nothing is acquiring;
  - closing the window is refused because a recording is in progress.

  The user has to kill the process, so the files are not finalised: npy headers up to 1 s stale, up to 8 MB of `.dat` lost from the BufWriter, `initial_state` wrong.
- **Failure scenario:** any unexpected panic in `read_block`/`live`/`parse`. I found no concrete panic path (indexing is guarded), so this is defensive.
- **Suggested fix:** send `AcquisitionStopped` from a drop guard inside the thread (or wrap the loop in `catch_unwind`). Let the Record button stop a recording whenever `is_recording()`, regardless of acquisition. The same applies if the recorder thread itself dies: the acquisition loop should stop sending and the GUI should show REC ERROR.
- **Severity:** low-medium (low likelihood, bad outcome). **Confidence:** plausible.

### 7. A repeated or backwards Rhythm counter reports ~4.3 billion lost samples and makes sample numbers non-monotonic
- **Where:** `crates/rhythm/src/parser.rs:84-99`.
- **What:**
  ```rust
  let delta = self.last_counter.map(|last| counter.wrapping_sub(last));
  ...
  health.dropped_samples.fetch_add(dl.wrapping_sub(1) as u64, ...);
  ```
  A duplicate frame (dl = 0) adds `u32::MAX` to `dropped_samples` and reuses the previous sample number, so the recorder writes a duplicate entry in `sample_numbers.npy`. A backwards step of k gives dl = 2³²−k, which shifts every later sample number by ~2³².
- **Failure scenario:** a valid-magic frame with a stale or duplicated counter (firmware or driver replay after a USB error). The health chip then shows `lost 4294967295`, and every later recorded sample number is offset by 4.29e9. Analysis tools that align on sample numbers break for the rest of the file.
- **Suggested fix:** treat `dl == 0 || dl > 2³¹` as an out-of-order or bad frame: count it in `bad_frames` (or a new counter), drop it, and don't update `last_counter`.
- **Severity:** low (needs a hardware or driver anomaly). **Confidence:** confirmed (logic); likelihood unknown.

### 8. On a write error the recording is dropped without a best-effort finalise
- **Where:** `crates/engine/src/record.rs:461-466, 534-540`.
- **What:** `fail(...); rec = None;` drops `Recording`:
  - `BufWriter`s flush in `Drop` with errors ignored;
  - the `.npy` headers keep the count from the last checkpoint (up to 1 s old) while their bodies may be longer;
  - `structure.oebin` keeps `initial_state: 0`;
  - nothing is `sync_all`ed.
- **Failure scenario:** a transient `EIO`, or `ENOSPC` on one stream, at minute 50 of a recording. All other files are left with inconsistent header vs body lengths. Readers that trust the header shape silently truncate up to 1 s; readers that memmap by file size see a sample_numbers/data length mismatch.
- **Suggested fix:** on error, try `checkpoint()` then `finish()` per file, ignoring individual failures, so every file that can be made consistent is. Make the failure more prominent than one chip, e.g. a modal or banner like `last_error`, since priority 1 is "lossless or loudly not".
- **Severity:** low-medium. **Confidence:** confirmed.

### 9. A config that fails to parse is replaced by defaults and then overwritten
- **Where:** `app/src/config.rs:388-396`; `app/src/app.rs` (`save_cfg` from `logic` and `on_exit`).
- **What:** `Config::load` logs a warning and returns `Config::default()`. The next debounced save, or `on_exit`, writes the defaults over the user's file.
- **Failure scenario:** a hand edit with a typo, or running an older build after a newer one added an enum variant. Then:
  - board settings revert, e.g. the 16-ch RHD2132 mode is lost and 16 unwired channels are recorded;
  - LEDs, DAC routes, CAR sets, trace windows and note presets are lost;
  - nothing is shown in the GUI.
- **Suggested fix:** on a parse error, rename the file to `config.json.bad-<time>` before continuing, and show the error in the GUI banner.
- **Severity:** low-medium. **Confidence:** confirmed.

### 10. Stop can hang the GUI if the board stops streaming without an error
- **Where:** `crates/engine/src/lib.rs:412-416` (`r.acq.join()` on the GUI thread); `crates/rhythm/src/oni_board.rs:1062` (blocking `read_frame`, no timeout).
- **What:** `stop_acquisition` sets the flag and joins. The loop checks `stop` only between blocks, and `read_frame` blocks indefinitely.
- **Failure scenario:** the board wedges or stops producing frames while the driver doesn't return an error (the D3XX 1.1 "timeout 0 = forever" class of bug, or a gateware stall). Stop, Apply, or closing the window freezes the whole GUI. `Engine::drop` would hang the same way.
- **Suggested fix:**
  - Join with a timeout (poll `is_finished()` for ~2 s). Then report "board not responding" and detach the thread, leaving the board lost (reopen required).
  - Ideally also ask liboni or the driver to abort the read: a reset from another thread is unsafe, but closing the context on exit is acceptable.
- **Severity:** low. **Confidence:** plausible.

### 11. Session directories can collide within one second, and existing files are truncated
- **Where:** `crates/engine/src/record.rs:499-512` (`%Y-%m-%d_%H-%M-%S`, then `create_dir_all` + `File::create`).
- **Failure scenario:** two forced "New session directory" recordings started within the same wall-clock second (or a clock step backwards) map to the same `experiment1/recording1`. `File::create` then truncates the first recording.
- **Suggested fix:** use `OpenOptions::create_new(true)` for `continuous.dat`/`structure.oebin` and bump the name on `AlreadyExists`.
- **Severity:** low (unlikely, but this is the only place where recorded data can be destroyed). **Confidence:** confirmed (mechanism).

### 12. Durability: no periodic fsync, no SIGTERM handling
- **Where:** `crates/engine/src/record.rs:357-368` (checkpoint flushes, no `sync_data`); no signal handler anywhere.
- **What:** data reaches the page cache within about 1 s, but is synced only at `finish()`. A session logout, `systemctl` stop, or OOM-kill (SIGTERM/SIGKILL) skips `on_exit`. Power loss loses the kernel's dirty writeback window (often 5–30 s).
- **Suggested fix:** `sync_data()` the main `.dat` every few seconds from the recorder thread (sequential writes make this cheap). Install a SIGTERM/SIGINT handler that sends `RecMsg::Stop` and lets `on_exit` run.
- **Severity:** low. **Confidence:** confirmed.

### 13. Smaller items
- **A note typed across the end of a recording is left out of it.** `app.rs` `logic` writes a note to the recording only if `is_recording()` at the moment it is *finished*, not when it was stamped. Opening `/` during the recording, clicking Stop with the mouse, then pressing Enter keeps the note only in `notes.log`. Low, confirmed.
- **Board settings can claim values the board doesn't have.** `OniBoard::apply_settings` sets `self.settings = new` before programming the board (`oni_board.rs:1001-1002`). If a register write fails midway, the board reports settings it doesn't have, so the GUI's "changed" check thinks Apply succeeded. Low.
- **An append can start from a pyramid-drawn image.** `frame.rs` "append" can append raw samples to a `Shown` image that came from the pyramid path, whose GPU filter state was never fed. The appended Band rows then start with a filter transient, and a larger chunk triggers `ensure()` reallocation, which clears the shown columns. It needs the pyramid to stop serving between two frames (a budget release crossing `t0`). Low, plausible.
- **Duplicate audio channels are possible.** `text_to_channels` uses `dedup()`, which removes only *adjacent* duplicates: "1, 5, 1" monitors channel 1 twice (louder, two pan positions). Low, confirmed.
- **The pool's no-allocation claim doesn't hold.** `acquisition_loop`'s pool (256) is smaller than the display (≈473 blocks), DSP, audio and pyramid (≈1880) queue depths. So whenever a lossy consumer lags, every block is freshly allocated, and with `Block::default()` it grows from zero capacity (several reallocations per block on the RT thread). Low, a perf note. Allocate replacement blocks `with_capacity`, or size the pool from the queue depths.

## Maintainability notes

- **Duplicated CAR window.** `App::car_palette` and `ViewsShared::car_palette` (`views.rs`) are ~90 nearly identical lines, each with a dead match arm (the `View` arm in the App version returns early; the `Global` arm in the view version edits throwaway `spikes`/`audio` locals). Extract one widget that takes `&mut ViewCar` plus an optional "apply to" row.
- **Two kinds of channel identity.** Per-row filters and µV overrides use `chan_key` ("A1:5"); DAC, CAR, audio and slope settings use global indices or the same key (`trig_channel`). Settling on one (keys) would remove finding 3 at its root.
- **O(n²) per-frame string work.** `chan_key` formats a `String` and scans all preceding channels; `chan_filters`, `band_key`, `view_chinfo` and the palette call it per channel, several times per frame per window. `drain()` also rebuilds `band_key` for every view on every window's frame. Precompute a per-layout `Vec<String>` of keys.
- **Stale doc.** `record.rs:16` says "The recorder thread receives every block while acquiring (recording or not)", but `acquisition_loop` sends blocks only while `recording` is set.
- **Unused parameter.** `acquisition_loop` takes `_health` unused, under `#[allow(clippy::too_many_arguments)]`; a small context struct would read better.
- **FFI nits.**
  - `oni.rs`'s `unsafe impl Send for Frame` comment says frames "move together with the owning Context". The real reason it's sound is that liboni refcounts the read buffer, so a frame may even outlive its context (and `OniBoard` field order does drop `ctx` before `pending`). Worth stating, since a future refactor might rely on the stated invariant.
  - `write_frame(&mut [u8])` needn't be `&mut`.
  - `Context::open` `unwrap()`s `CString::new` on a caller string.
- **Long lines.** Many lines are 200–400 characters (e.g. `oni_board.rs:1014`, `views.rs` closures, `app.rs` chips), which makes diffs and review harder. A `rustfmt.toml` with a moderate `max_width` would help.
- **Tests.** Coverage is good where it matters most (parser, recorder output, DSP, audio texture, pyramid vs brute force, sweeps, slope trigger). Missing tests for the review/pyramid mapping across a gap (finding 4) and across an acquisition restart (finding 2) would have caught both. A recorder test for the error path (simulate a failing writer) would pin finding 8.

## What is done well

- **The lossless/lossy split is right and simple.** It is one bounded, back-pressured recorder queue whose stall is absorbed by board DRAM and measured (`rec_backpressure_us`). Every other consumer is `try_send` with a drop counter. Recording is a memcpy of the raw blocks, so display/DSP/CAR settings can't touch the file.
- **Gap handling in the parser is careful.** A discontinuous frame is re-submitted to a fresh block without double counting, a bad frame shows up as a counted gap, and both are tested.
- **The register port is disciplined.** It is a literal port of the stock plugin with `DIFF:` markers only where failures are made visible (PLL timeout, calibration timeout). It comes with a `regdump` harness for diffing against C++, plus a hardware-safety audit (volatile registers only).
- **Unsafe code is minimal and correct.** Raw byte views of `i16`/`f64` slices are guarded by a little-endian `compile_error!`, and the liboni wrapper's lifetimes check out against the vendored source.
- **Crash-tolerant files.** The fixed-width `.npy` header rewritten every second gives readable files after a crash, and the config is saved write-then-rename.
- **The audio chain matches its stated psychophysical intent.** It has a held calibration, an exactly linear limiter below 0.5 FS, a flat windowed-sinc resampler, and a reference A/B mode. It has tests that encode the goals (rate invariance, amplitude-ratio preservation, hash audibility, CAR).
- **The GUI architecture handles Wayland realities well.** Deferred viewports, the `Edit` queue (one settings snapshot per frame), `VecDeque` staging, and chunked uploads under the storage-binding limit were all fixed with measured reasons recorded in comments.
- **The pyramid design is solid.** It is incremental, multi-level, chunked for a RAM budget and verified against brute force; the issues above are in its lifecycle and locking, not its core.
